## 2. 実装上の判断（仕様の範囲内で決めたもの）

| 項目 | 内容 | 理由 |
| --- | --- | --- |
| 空席の扱い | ホストはいつでも開始でき、空席はCPUが埋める。4人そろうと自動で開始 | 1人でもテストできる。仕様の「最大4人」に合う |
| 切断中のプレイヤー | ドラフトでは時間切れで自動指名（設計書 3-5）。再接続すると最新の状態を受け取る | 設計書 23-1「通信切断後に復帰できる」 |
| GK の表示能力 | 設計書 4-1 どおり、GK も PAC〜PHY の6項目。値はデータベースのとおり | 確定仕様のとおり |
| 表示能力・OVR | データベースの値をそのまま使う（内部能力から計算しない） | 設計書 4-2「算出してもよい」の範囲。データを正とするため |
| ポジション別評価 | 主ポジションでの評価＝カードのOVR。他のポジションは内部能力から計算した比率と適性外の減点で決める | カードのOVRと編成画面の数字をそろえるため |
| SIM の能力の水準 | SIM は内部能力の「形」（得意・不得意の比率）を使い、全体の水準はカードのOVRに合わせる（補正係数は 0.67〜1.13） | データの内部能力はOVRより平均8%高く、選手ごとのずれも大きい。そのままだとOVRと強さが一致せず、得点も多すぎた（1試合4.2点） |
| プレースタイル | データベースにないため、主ポジションと内部能力から自動判定（ケミストリー用） | 設計書 5-5 のケミストリーに必要 |
| 顔の描き方 | 実写の肖像（決定事項 21）がある選手は実写カード、ない選手はイラスト（SVG で描いてカード画像に焼き込んだもの）。どちらのカードかは `portraits.json` に載っているかで決まる（`cardArtOf`） | 決定事項 20・21・23 |
| 実写の肖像の保存 | 生成した画像は 640×640 の JPEG で `data/player-db-v1/portraits/` に保存し、モデル・Figma のノード・生成日を `portraits.json` に記録。カードはそこから `photo_cards.py` で作り直せる | Figma の画像URLは7日で切れるため |
| 丸アイコン | カードの種類ごとに顔の位置が違うため、切り抜く範囲を分ける（実写：x131・y70・250px、イラスト：x176・y146・160px） | どちらのカードでも顔が丸の中に収まるように |
| 顔の重複防止 | 肌の色・髪型・髪色・ひげの組み合わせが全員異なるように生成し、テストで確認 | 「全て別々の顔」を保証するため |
| 元のカード画像 | `data/player-db-v1/cards/` に元データとして保存。配信用は `assets/cards/`（描き込み後） | いつでも描き直せるようにするため |
| 旧カード（240人） | D1 では削除せず無効化（`is_active=0`）。過去のドラフト・試合の記録はそのまま残る | 履歴の整合性のため |
| 管理者の権限 | owner / admin / viewer の3種類（暫定）。viewer はカード閲覧のみ | 設計書 24-11 が未確定のため最小限 |
| 管理サイトの未実装ページ | メニューに出さない | 未実装機能を実装済みに見せないため（設計書 0-4） |
| WebSocket 認証 | `POST /api/rooms/:id/ticket` で発行する60秒有効の署名付きチケット | ブラウザのWebSocketはヘッダーを付けられず、セッショントークンをURLに出さないため |
| 管理者の2段階認証 | TOTP（RFC 6238）。`ADMIN_REQUIRE_2FA=true` の環境（staging・production）では必須。ローカル環境だけ任意 | 設計書 20-4。ローカルで確認しやすくするため |
| 公開環境の最初の管理者 | GitHub Actions の Create admin で作成（パスワードは GitHub のシークレット）。2段階認証のキーは管理サイトへの初回ログイン時に、パスワードを確認したうえでその場で表示して登録（登録の開始と完了は操作ログに記録） | キーや パスワードを CI のログやチャットに出さないため |

| 通貨の残高と台帳（Phase 4） | 残高は通貨ごとに別の列（0未満は DB の制約で不可）、増減は台帳に1行ずつ。報酬は「ユーザー×報酬キー」の一意制約で1回だけ。ガシャ・交換は「ユーザーごとの操作番号」と「取引ID」で二重実行を防ぐ | 設計書 8・9・18 の「二重付与・二重消費の防止」 |
| ログインボーナスの受け取り | アプリを開いた時に自動で受け取る（日本時間の1日1回） | 受け取り忘れを防ぐため |
| 保留していた報酬の支払い | 残高を表示する時に、まだ支払っていないシーズン報酬・ソロ課題・イベントの報酬を確認して支払う（シーズンは締めた時にも支払う） | 決定事項 40。リーグ終了時に書き込みが失敗しても後で支払われる |
| Collection Draft のルーム | マッチング（ホームの「Collection Draft」）でだけ参加でき、招待コードでは参加不可。ホストはいつでも開始でき、空席はCPU | クイックドラフトと同じ遊び方にするため |
| テスト付与の種類 | COINS・無償GEMS・有償GEMS（配布）・有償GEMS（購入扱い）・交換ポイント。有償GEMS（購入扱い）は消費順の確認用で、staging とローカルだけ | 決定事項 42。本番では API が常に拒否 |

| アクティブの定義（Phase 5） | その日（日本時間）に何らかの記録（ゲームを開いた・対戦した等）があったプレイヤー。ログイン失敗は数えない | 設計書 12-5・12-6。ログインし直さずに遊ぶ人も数えるため |
| 集計の更新 | 終わった日は管理サイトを開いた時に一度だけまとめる（定期実行なし）。今日の分は開くたびに計算 | シーズンと同じ「必要になった時に処理」。Workers の定期実行を使わずに済む |
| 配布の実行 | 50人ずつに分けて実行し、管理サイトが完了まで続けて呼ぶ。途中で止まっても続きから再開でき、二重に付与しない | Workers の1回の処理の上限に収めるため |
| フィードバックの回数制限 | 1人1日10件まで | いたずらの大量送信を防ぐため |

| 模擬ストアのレシート（Phase 6） | サーバーが署名したレシート（WS_TICKET_SECRET から作った別の鍵）。検証ではユーザー・購入・商品が一致するかを確認。本番（ENVIRONMENT=production）では使えない | 実際のストアにつなぐ前に「購入→検証→付与→返金」を通しで確かめるため（決定 52） |
| 購入した GEMS の内訳 | 価格と同じ数を「有償GEMS（購入）」、おまけと初回ボーナスを「有償GEMS（配布）」として記録。初回ボーナスは商品ごとに1回 | 返金で回収する量と、未使用の購入分を正しく数えるため |
| 会員の毎日の GEMS | ログインボーナスと一緒に受け取る（日本時間の1日1回） | ログインボーナスと同じく受け取り忘れを防ぐため |
| 会員の自動更新（模擬） | 模擬ストアでは管理サイトの「更新・解約・期限切れ」で確認。実際のストアの通知の受信は接続時に作る | ストアの通知はアプリとストアの設定がないと受け取れないため |
| Season Pass の経験値 | 1日の対戦報酬の枠（10リーグ）があるリーグだけ。1位は +50 | 対戦報酬と同じ上限にして、短時間の大量周回を防ぐため |
| Season Pass のカード報酬 | 持っていないカードから選ぶ。全部持っている時は Standard の交換ポイント（Epic：1,000、Legendary：3,000） | 重複を避けるため |
| 公開中のガシャの変更 | 変更内容の入力が必須。天井を引き継ぐ単位（シリーズ）は公開後に変更できない | ガシャ画面の変更履歴に理由を出すため。天井の数え方が途中で変わらないように |
| 売上の模擬分 | 模擬ストアの売上は「実際の売上ではない」と表示する（本番では模擬ストアがないので0） | 設計書 0-4「ダミーデータを本物として表示しない」 |
